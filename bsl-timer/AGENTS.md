# Инструкции для работы с BSL-Timer

## Общение и локализация

- Общаться с пользователем по-русски.
- В общении использовать имя Наташа и женский род.
- Поддерживать русский и английский интерфейсы (RU/EN).
- При изменении пользовательских текстов обновлять обе локализации.
- Проверять размещение текста и элементов управления в обеих локализациях.

## Контекст проекта

BSL-Timer — настольный таймер для Windows на Tauri 2, Rust,
Vanilla JavaScript, Vite и WebView2.

Перед работой читать документы, относящиеся к задаче:

- README.md — текущее состояние проекта и возможности редакций.
- CHANGELOG.md — история изменений.
- docs/release-0.7.2.md — историческая запись о релизе и проверке обновлений.
- docs/taskbar-icon-investigation.md — завершённое расследование
  динамической иконки панели задач.
- docs/end-signal-plan.ru.md и docs/end-signal-plan.md —
  требования к сигналам, устройствам вывода и Информеру.

Учитывать даты документов: исторические планы и ограничения могут быть
заменены более поздними решениями. Например, текущая модель редакций
предусматривает один таймер и одно датированное событие во Free,
несколько таймеров и датированных событий в Pro.

Общие механизмы BSL-World предоставляет локальная зависимость
@bsl-world/desktop-core. Не дублировать их без необходимости.
Менять bsl-core, если это входит в явно поставленную задачу. При необходимости расширить область задачи согласовать это с пользователем.

## Неприкосновенность функционала вне задачи

- Жёсткое правило пользователя: изменять только те части программы и тот
  функционал, которые явно обсуждены в текущей задаче. Остальные части,
  поведение и интерфейс неприкосновенны.
- Не выполнять попутные улучшения, рефакторинг, упрощения, переоформление
  или изменение поведения вне согласованной задачи.
- Исправляя дефект, сохранять остальное существующее поведение, в том числе
  обновление данных во времени, взаимодействия и внешний вид. Отсутствие
  этого поведения в описании задачи не означает разрешения его изменить.
- Если исправление требует затронуть функционал за согласованными границами,
  сначала объяснить необходимость и получить прямое согласование пользователя.
- Перед завершением проверить diff на соблюдение границ задачи и проверить
  сохранность связанного существующего поведения. Проверки отдельных снимков
  данных недостаточны для сценариев с изменением состояния во времени.

## Точечные исправления и защита от возврата дефектов

- Исправление применять точечным патчем к текущему содержимому файла:
  менять только фрагменты, непосредственно необходимые для указанного дефекта.
- Запрещено заменять существующий файл целиком версией из архива, старой ветки,
  шаблона или заранее подготовленного файла, в том числе через Copy-Item.
  Старые файлы использовать только для сравнения; переносить из них отдельные
  необходимые изменения с проверкой текущего контекста.
- Перед правкой сохранять исходную точку актуального файла, включая все
  незакоммиченные изменения. Если контекст патча не совпал, перечитать файл
  и разобраться в расхождении; не обходить ошибку перезаписью файла целиком.
- После правки сравнивать результат с исходной точкой задачи. Изменения
  вне согласованных фрагментов должны отсутствовать; ранее принятые исправления
  и чужие изменения сохранять. Проверять diff относительно начала задачи,
  а не только относительно последнего коммита, который может отставать.
- Для затронутого механизма перечислять прежние исправленные дефекты
  и выполнять соответствующие регрессионные проверки. Если проверка не выполнена,
  явно указывать это и не объявлять прежнее исправление сохранённым по одному diff.
- Для захвата экрана проверять фактическое присутствие окна на готовом снимке
  и восстановление после захвата. Смена флага WinAPI, код возврата и отдельный
  успешный кадр не доказывают надёжность обычного PrtScn/Win+Shift+S.
- Изменение архитектуры, перенесение механизма в Core и оптимизация не отменяют
  эти требования. Если необходим больший объём правок, сначала объяснить
  конкретную необходимость и согласовать расширение задачи.

## Git и сохранность изменений

- Перед любыми изменениями проверять доступность Git, корень
  репозитория, текущую ветку, git status и существующий diff.
- Для существенной задачи обеспечить сохранённую исходную точку;
  если для этого нужен коммит, запросить разрешение пользователя.
- При откате отменять только изменения текущей задачи, сохраняя остальные.
- Не применять git reset --hard и git clean без прямого указания пользователя.
- Если репозиторий недоступен, сообщить об этом до изменения файлов.
  Не создавать новый репозиторий автоматически.
- Сохранять чужие незакоммиченные изменения, включая новые файлы.
- Не откатывать, не перезаписывать и не включать чужие изменения
  в свою работу без прямого указания пользователя.
- Если собственные изменения пересекаются с существующими,
  сначала изучить их и сохранить исходный замысел.
- Перед завершением работы проверить итоговый diff и описать
  фактически внесённые изменения.

## Проверка поведения

- Выполнять проверки, соответствующие задаче и разрешённому объёму работы.
- Не считать успешную сборку доказательством правильной работы интерфейса.
- Для изменений интерфейса проверять видимое поведение: размеры окон,
  обрезание содержимого, доступность кнопок, фокус и локализацию.
- Проверять соответствие размеров окна выбранному размеру шрифта, отступы от границ, отсутствие наложений и обрезания элементов в RU/EN. При изменениях, затрагивающих редакции, проверять Free и Pro.
- При затрагивании масштабирования проверять Small, Normal и Large;
  при изменении оформления — соответствующие темы и режимы окна.
- Для изменений трея, панели задач, позиционирования и обновлений
  учитывать различия между режимом разработки и установленным приложением.
- Отдельно указывать, что проверено автоматическими тестами,
  сборкой и визуальной проверкой установленного приложения.
- Если какая-либо проверка не выполнена, прямо сообщать об этом.
  Не представлять ожидаемый результат как проверенный.

## Версии и выпуск

- При проверке версии сопоставлять package.json,
  src-tauri/tauri.conf.json и src-tauri/Cargo.toml.
- Если добавлены возможности или внесены исправления и готовится новый
  дистрибутив, самостоятельно повышать номер версии без отдельного вопроса.
- Не создавать разные дистрибутивы одной редакции с одинаковым номером версии.
- Согласованно обновлять версию в package.json, конфигурации Tauri,
  Cargo.toml, lock-файлах и информации о новых возможностях.
- Создавать коммиты, выполнять push и выпускать релиз
  только по прямому указанию пользователя.
- Публиковать артефакты и менять производственные манифесты обновлений
  только по прямому указанию.
- Учитывать отдельные артефакты и цели обновления Free/Pro.
  Pro не является публичной загрузкой.
- При выпуске сохранять пользовательские данные и настройки,
  проверять подписи и соответствие артефактов редакции.

## Статус Информера

По проверке пользователя установленных версий начиная с 0.11.0
Информер отображался при обычном отсчёте и после истечения времени.
Предполагаемая регрессия не подтвердилась. Причина прежнего
локального сбоя неизвестна.

Не считать исчезновение Информера подтверждённым дефектом.
Расследование и исправления сейчас не требуются; возвращаться
к ним только при новой задаче или новых данных пользователя.
