# Glass: потеря прозрачности и цикл смены оформления — исследование 3 ноября 2026

Статус: исследование кода и изолированных моделей. Исправления в код приложения
не вносились. Установленное приложение не запускалось, не закрывалось, его темы
и пользовательские данные не менялись. Воспроизведение на рабочем ПК не проводилось.

## Сообщение пользователя

На хостовой машине Glass внезапно приобрёл признаки тёмного системного
оформления и потерял прозрачность. Попытка выбрать светлую тему привела
к непрерывным изменениям/перерисовкам несколько раз в секунду. Остановить
получилось только через Task Manager. Точный момент начала и действия перед
первым изменением не установлены. Связь с прежним PrtScn/Win+Shift+S не доказана.

## 1. Подтверждённый дефект: обратная пересылка устаревших тем

`src/appearance-mode-settings.js:80–112` совмещает применение оформления
с записью в общее для окон хранилище: `setItem(APPEARANCE_MODE_STORAGE_KEY, mode)`.
Обработчики входящих `storage`-событий в `main.js:2178`, `settings.js:1617`,
`about.js:117`, `whats-new-window.js:129` и `date-countdown-window.js:740`
передают `event.newValue` обратно в эту же записывающую функцию.

Если один переход успел полностью разойтись по окнам, повторная запись
того же значения безвредна. Если в очереди накопились разные значения,
старое событие возвращает предыдущую тему в хранилище, порождая новые события
для других окон. Те снова записывают старые значения. Нужны как минимум
два окна и два неуспевших обработаться разных значения.

Изолированная модель использует настоящие `applyAppearanceMode` и
`watchAppearanceMode`, хранилище в памяти и соответствующий обработчикам страниц
путь применения входящего режима. Браузер, Tauri, native renderer и пользовательский
профиль не задействованы. Она моделирует допустимый порядок накопившихся событий,
а не утверждает, что именно такой порядок был в сеансе пользователя.

| Сценарий модели | Результат |
| --- | --- |
| Один переход Glass → Light, два окна | Очередь опустела после 2 событий |
| Два накопившихся значения Dark → Light, два окна | Цикл: состояние на шагах 1 и 9 совпало; после 500 обработок очередь не пуста |
| Light → Glass, два окна | Цикл: состояние на шагах 1 и 5 совпало; после 500 обработок очередь не пуста |
| Light → Glass, три окна | Цикл: состояние на шагах 2 и 10 совпало |
| Модель с применением входящих событий без обратной записи и чтением актуального режима | Очередь опустела: 3 события для двух окон, 6 для трёх |

Совпадение состояния включает хранилище и оставшуюся очередь; при детерминированных
обработчиках это подтверждает цикл модели. Проверка старого кода 1.1.3 также
дала циклы: дефект не возник впервые в исправлении вспомогательных окон 1.1.7.

Это сильное объяснение повторяющихся смен оформления после попыток переключиться.
Однако входящие события и DOM-состояние зависшего процесса не сохранены:
срабатывание именно этого пути в пользовательском сеансе ещё не доказано.

## 2. Подтверждённый дефект: незавершённый захват оставляет служебную маску в Light

`bsl-core/utils/glass.js:68–84` временно ставит на корневой элемент атрибут
прохода `base` или `mask`, чтобы снять основу и надписи раздельно. Стили маски
не ограничены только `data-appearance="glass"`. Удаление атрибута выполняется
в `finally` после завершения ожидаемой операции.

При смене материала (`glass.js:138–147`) поколение меняется, нативная поверхность
скрывается, но ожидающий кадр не отменяется. `AbortController` срабатывает
только при полном `dispose` (`glass.js:152–159`). Rust-команда CapturePreview
ждёт callback через `rx.recv()` без таймаута (`native/window/src/glass.rs:75–108`).

Вторая изолированная модель использует настоящий `createGlassSurface`
с фиктивными DOM и native bridge. После нормального первого кадра модель
намеренно не завершает callback прохода INK и переключает режим на Light.
Через 100 мс проверка даёт:

```json
{
  "beforePass": "mask",
  "appearance": "light",
  "afterPass": "mask",
  "captureCompleted": false,
  "afterDisposePass": null
}
```

Значит, обычное переключение темы не гарантирует очистку служебной маски.
Она продолжает скрывать текст/фон/границы уже у Light. Полный dispose очищает её.
Это объясняет возможность смешанного или повреждённого оформления, но модель
**вводит зависший callback искусственно**: фактическое зависание CapturePreview
в пользовательском процессе пока не подтверждено.

## 3. Вероятный первичный триггер: потеря/сбой графического захвата

Glass зависит от Desktop Duplication, D3D11 и отдельной Composition-поверхности.
При ошибке native renderer выставляет `needs_reset` и повторяет попытку через
1000 мс (`glass_surface.cpp:350`). При полном сбросе сначала убирается
`pane.Brush`, затем пересоздаются графические ресурсы (`:321–324`).
При повторных ошибках нет ограниченного числа попыток и согласованного
перехода в стабильное обычное оформление; JS не получает от этого таймера
состояние «графический слой неисправен». Это уязвимое место, способное оставить
видимую часть интерфейса без корректного материала.

Microsoft документирует, что Desktop Duplication может терять доступ при смене
рабочего стола, видеорежима и некоторых полноэкранных переходах; интерфейс
нужно создавать заново:
[IDXGIOutputDuplication::AcquireNextFrame](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe).

В журнале этого сеанса нет кода ошибки DXGI/WebView2 и стека зависания.
Поэтому обвинять драйвер, снимок экрана, сон или монитор как установленную
причину нельзя. Первоначальная потеря прозрачности остаётся неустановленной.

## Что следует исправлять в отдельной задаче

1. Разделить применение внешнего состояния и пользовательскую запись настройки.
   Входящие `storage`-события не должны повторно публиковать устаревшие значения.
   Должен побеждать актуальный выбор, без отражения событий между окнами.
2. При выходе из Glass отменять ожидающие проходы и немедленно снимать маску,
   не ожидая callback. Поздние кадры от прежнего поколения не должны возвращать
   старую поверхность. Добавить ограничение ожидания CapturePreview.
3. Согласовать отказ native renderer и обычный материал окна: ограниченное
   восстановление, освобождение принадлежащего Glass состояния и стабильный
   выход из неудачного восстановления.
4. Сохранить небольшой журнал переходов: выбранный и фактический материал,
   источник изменения, поколение/сеанс, фаза захвата, код ошибки и повторы.
   Не сохранять изображения рабочего стола, содержимое буфера или тексты таймеров.
5. Проверять задержанные события разных окон и зависший callback, а не только
   последовательные быстрые переключения при исправной графике.

Исправления затронут Timer и общий Desktop Core. В этой задаче разрешено
исследование: производственный код и Core не менялись, сборка и публикация
новой версии не выполнялись. Проблему пропорций Glass и ленты дат не затрагивать.
